# Decision 06 — MFA Strategy

## The Decision

**How do you handle MFA re-enrollment when users move from Okta to Entra authentication?**

This is not a question of *whether* users must re-enroll — **they must, without exception.** Okta MFA factors are not portable to Entra. Zero Okta authentication methods migrate:

| Okta Factor | Why It Doesn't Port |
|-------------|---------------------|
| Okta Verify (push/TOTP) | Bound to Okta's push service infrastructure; TOTP seeds are Okta-custody |
| FIDO2 / WebAuthn security keys | Credential bound to Okta's RP ID (`yourdomain.okta.com`); different RP ID in Entra means all keys must be re-registered |
| Google Authenticator / TOTP apps | TOTP secret seeds are generated by Okta and not exportable |
| SMS / Voice call | Numbers would technically transfer, but Entra provisioning requires fresh enrollment |
| Email OTP | New enrollment required under Entra's authentication methods |
| Hardware TOTP tokens (Yubico OTP) | Seed material is not exportable from Okta |

**Every user who authenticates through Entra after cutover must register at least one Entra authentication method before their first login.**

---

## Options

### `reenroll_campaign`
A structured, time-boxed MFA registration campaign is run before cutover. Users are notified via email/Teams/Slack, directed to `aka.ms/mfasetup` (or an internal portal), and given a deadline. A registration status report is monitored daily. Users who miss the deadline are blocked at cutover until they register.

### `passkey_bootstrap`
The migration is used as an opportunity to move the org to passkeys (FIDO2, Windows Hello for Business, platform authenticators) as the primary MFA. Users enroll a passkey as their first Entra authentication method. Phishing-resistant by design. Eliminates SMS/OTP as the enrolled fallback.

### `per_population`
Different MFA enrollment strategies are applied per user segment. Example: knowledge workers get passkey bootstrap; remote/BYOD workers get Microsoft Authenticator campaign; privileged users get FIDO2 security key pre-provisioning; contractors get temporary access pass (TAP) bootstrap.

---

## Trade-offs

| Option | Pro | Con |
|--------|-----|-----|
| `reenroll_campaign` | Familiar to most organizations. Flexible — users choose their preferred method from what's enabled. Lower friction for end users. | Takes time to run. Non-compliant users create blockers at cutover. Campaign management overhead. Phishing-susceptible methods (SMS, OTP) may be enrolled. |
| `passkey_bootstrap` | Best security outcome — phishing-resistant from day one. Aligns with Microsoft's Entra passwordless roadmap. Reduces helpdesk volume for MFA reset long-term. | Higher per-user onboarding effort. Requires user device compatibility validation (Windows Hello, Face ID, etc.). Legacy/shared workstations may not support passkeys. |
| `per_population` | Tailored to real-world heterogeneity. Right method for each user type. Can be phishing-resistant for high-privilege users while pragmatic for general staff. | Most complex to plan, communicate, and track. Requires population segmentation before running the campaign. |

---

## Recommended Default

**`reenroll_campaign`**

**Rationale:** A well-run registration campaign is the most broadly applicable approach. It gives users choice (within the methods you enable), is familiar from any previous MFA rollout experience, and has a clear completion metric (% of users with at least one registered method).

Run it in parallel with the coexistence phase — users register Entra MFA while still authenticating through Okta. By the time cutover begins, registration should be at >95% for each planned cohort.

**Strongly consider upgrading to `passkey_bootstrap` if:** The org has Windows 11 on managed devices, a Microsoft 365 E5 license (which includes FIDO2 support and Windows Hello for Business at no additional cost), and executive buy-in for a passwordless initiative. The migration is the single best moment to eliminate SMS/OTP — retrofitting after migration is much harder.

---

## The Re-Enrollment Seam

The re-enrollment seam is the most operationally sensitive moment in the migration. Plan it explicitly:

1. **Enable combined registration** in Entra: `aka.ms/mfasetup` must be accessible to all users
2. **Enable Temporary Access Pass (TAP)** as a bootstrap method — helpdesk uses TAP to onboard users who can't self-register
3. **Set an Authentication Methods policy** in Entra that enables the methods you want (Microsoft Authenticator, FIDO2, software OATH tokens) and disables legacy methods (SMS, voice call) if you're going phishing-resistant
4. **Monitor registration** via the Entra Authentication Methods Activity report — aim for a named completion percentage before each cutover wave starts
5. **Communicate the deadline clearly** — users who miss it will be blocked by Conditional Access at their first Entra-authenticated sign-in
6. **Plan for helpdesk surge** — first week post-cutover always generates MFA reset tickets; pre-authorize TAP issuance for the support team

> ⚠️ **Do not deactivate Okta MFA before Entra MFA is confirmed registered for a user.** During coexistence with `okta_idp_into_entra` federation direction, Okta MFA is still the active factor. Removing it before the user has Entra MFA creates a window with no MFA at all.

## Method Mapping (Okta → Entra)

| Okta Authenticator | Entra Authentication Method | Notes |
|--------------------|-----------------------------|-------|
| Okta Verify (push) | Microsoft Authenticator (push) | ✅ Functional equivalent — new enrollment required |
| Okta Verify (TOTP) | Microsoft Authenticator (OATH software token) | ✅ Functional equivalent — new seed |
| WebAuthn / FIDO2 | FIDO2 Security Keys | ✅ Same keys, re-registration required (different RP ID) |
| Google Authenticator | Software OATH token | ✅ Equivalent function — new seed |
| Windows Hello (via Okta FastPass) | Windows Hello for Business | ✅ Equivalent — new enrollment under Entra tenant |
| SMS OTP | SMS (if enabled) | ⚠️ Consider disabling in Entra — phishing-susceptible |
| Voice call | Voice call (if enabled) | ⚠️ Same concern |
| Hardware TOTP (YubiKey OTP) | OATH hardware tokens | ⚠️ Requires re-programming seed in Entra — OTP mode only |
| Okta Email factor | Email OTP | ✅ New enrollment |

---

## Rollback Implication

- **`reenroll_campaign` rollback:** If coexistence uses `okta_idp_into_entra`, Okta MFA is still active — users who registered Entra MFA have not lost anything; they still have Okta MFA for Okta-authenticated apps. Rollback is clean.
- **`passkey_bootstrap` rollback:** Passkeys registered in Entra cannot be used in Okta. If the org rolls back to Okta as IdP, users must re-enroll in Okta MFA from scratch. **Passkey bootstrap creates a hard dependency on Entra proceeding.**
- **`per_population` rollback:** Depends on which population you're rolling back. Per-cohort rollback complexity varies.
